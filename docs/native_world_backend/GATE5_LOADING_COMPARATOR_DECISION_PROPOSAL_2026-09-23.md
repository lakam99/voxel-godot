## Recommended approval question and candidate envelope

Ask the user to approve an **absolute loading policy before** the final five-cold/five-warm run. The reviewable candidate is: every cold New Game menu-input-to-actual-playable-ready duration ≤90 seconds; every paired warm Continue ≤45 seconds; loading Main callback max ≤33 ms; no missing loading overlay frames or modal re-entry after ready. The cold number has the two G2 observations as a limited empirical anchor. The warm 45-second number is an **unverified product target** and needs explicit approval or a predeclared replacement after a separately labeled diagnostic pilot. Neither number may be selected or relaxed after seeing final matrix timings. If the user does not approve a duration envelope, keep the runner fail-closed and report the loading row blocked.

For a complete **stage/UI envelope**, propose approval of first visible loading frame within 1 second of input, loading-frame gap p99 ≤33 ms and max ≤100 ms, with the existing no-single-Main-callback-above-33-ms rule. These three UI numbers are proposed usability limits, not validated historical controls. Record all stage start/end times and `startupReadinessDomains`, including terrain collision, required tutorial town manifest/home/door/NPC assignments and navigation publication, so early UI release cannot shorten the measured load. Keep progress visible until those domains are ready and observe at least 60 post-ready frames without re-entry. The runner already records first-frame latency, loading frame p99/max, stage distributions, full-loading Main callback maximum, overlay continuity and post-ready modal frames, but currently **does not compare first-frame or frame-gap values to pass-affecting thresholds**. The chosen policy must be implemented and unit-tested in the evaluator *before* final runs; it cannot be claimed from the current summary alone.

Do **not** promote G2's `warm ≤1.10 × reusable paired cold work` wording unchanged. `tools/lib/world-streaming-loading-matrix.mjs` currently computes `warmToColdRatio` from total input-to-ready times, without identifying reusable cold-stage work, and marks duration comparison non-pass-affecting. Either define a stable, independently measured comparable stage subset before approval, or omit that ratio from the release rule. The proposed absolute warm limit still tests Continue latency. A diagnostic pilot, if authorized, can inform a new predeclared proposal but cannot itself be a final Gate 5 pass.

## Existing runner guarantees and final-run conditions

`tools/lib/world-streaming-loading-matrix.mjs` already requires ten distinct processes, three controlled known-seed cold launches plus two fresh-seed cold launches, each paired with warm Continue. Cold uses fresh isolated empty `APPDATA`/`LOCALAPPDATA`, stronger than clearing only generated artifacts. The runner hashes source/binaries and paired v2 save files, checks actual seeds, real renderer/window/render target at 1920×1080, gameplay readiness, overlay continuity, error-free logs and natural zero-owned-process exit. Its current policy deliberately returns `gate5_blocked_duration_policy_unresolved`, `gate5LoadingAccepted:null`, and a nonzero Gate 5 exit even if functional diagnostics pass. Unit tests explicitly guard that behavior. Preserve these checks and run one measured headed sample at a time on the frozen final native source, installed binaries and exact saves.
