**Product direction received: loading need not meet a 90-second total; it must stay responsive.** This supersedes the earlier 90/45/1.10 candidate as a release rule. Exact new responsiveness numbers still need confirmation before final measured runs. No loading run or threshold change was made for this review. `gate5LoadingAccepted` remains `null` and Gate 5 remains open. ## Control search

The suggested `voxel-biome-world-godot-sep12-smooth-control` checkout is commit `ede61d2127d4ca055cf6449694b232917633014d` (September 12). Its local `artifacts/citadel-runtime-integration/` has no matching loading report, and the commit predates both `tools/run-world-streaming-maturity-loading-matrix.mjs` and `scenes/testing/WorldStreamingMaturityLoading.tscn`. Its checked-in loading implementation record calls 90 seconds **provisional** and describes an integrated approach failure; it provides neither five paired menu-input timings nor equivalent final readiness/cache/save conditions. The migration plan itself labels that checkout a *potential*, unverified smooth control. Thus there is **no verified like-for-like smooth-control comparator** available to adopt. Do not use its name or commit as a numerical baseline.

The G2 profile explicitly says no equivalent smooth control was found. Its 90-second cold proposal comes from two corrected fresh New Game observations of 75.280 and 77.935 seconds plus roughly 15% margin, while the 45-second warm and 1.10 reusable-work ratio lack a paired final-build control in that report. The 127.627-second snapshot in the migration plan is a known regression, not a successful standard. None now supplies a hard total-duration acceptance threshold.

## Responsiveness decision to freeze before final runs

The Gate 5 loading row should pass on **continuous responsiveness and complete readiness**, with cold/warm input-to-ready and stage durations reported as diagnostics. Do not fail a completed, responsive load solely because it exceeds 90/45 seconds, and do not use the 1.10 ratio as a release threshold. A process watchdog remains a separate noncompletion/lifecycle guard: timeout means the sample did not finish and fails functional acceptance, not that it exceeded a user-experience speed target. Keep its configured timeout, actual elapsed time and reason in the report.

For a measurable **responsiveness envelope**, recommend first visible loading frame ≤1 second after menu input, loading presentation frame-gap p99 ≤33 ms and max ≤100 ms, and full-loading Main callback max ≤33 ms. The 33 ms Main limit already affects the hardened runner; 33 ms p99 and 100 ms max mirror the original Gate 5 presentation/stall limits, while 1 second first-overlay latency is a new usability proposal. Confirm these numbers with the user before making them pass-affecting. Require the overlay on every observed loading frame, an honest stage/readiness timeline and no modal re-entry over at least 60 post-ready frames. Record stage durations and `startupReadinessDomains`, including terrain collision, required tutorial town manifest/home/door/NPC assignments and initial navigation publication, so early overlay removal cannot shorten the measured load. An honestly unchanged stage can remain visible while work continues, but a periodic progress heartbeat should report its owner, pending work/age and last completed unit; propose ≤5 seconds between such heartbeats while loading, subject to confirmation. If no source work is active, a stage must complete or fail instead of emitting a cosmetic percentage. The runner already records first-frame latency, frame p99/max, stage distributions, full-loading Main callback maximum, overlay continuity and post-ready modal frames, but currently **does not make first-frame or frame-gap values pass-affecting or detect a semantic progress heartbeat gap**.

`tools/lib/world-streaming-loading-matrix.mjs` computes `warmToColdRatio` from total input-to-ready times, without identifying reusable cold-stage work. Retain that and the former 90/45 comparisons as clearly labeled diagnostics only; remove language implying they can decide release. A diagnostic pilot may validate instrumentation and reveal an unresponsive stage, but it is not a final Gate 5 pass and must not be used to choose thresholds after final data are visible.

## Existing runner guarantees and final-run conditions

`tools/lib/world-streaming-loading-matrix.mjs` already requires ten distinct processes, three controlled known-seed cold launches plus two fresh-seed cold launches, each paired with warm Continue. Cold uses fresh isolated empty `APPDATA`/`LOCALAPPDATA`, stronger than clearing only generated artifacts. The runner hashes source/binaries and paired v2 save files, checks actual seeds, real renderer/window/render target at 1920×1080, gameplay readiness, overlay continuity, error-free logs and natural zero-owned-process exit. Its current policy deliberately returns `gate5_blocked_duration_policy_unresolved`, `gate5LoadingAccepted:null`, and a nonzero Gate 5 exit even if functional diagnostics pass. Update that policy only after the responsiveness numbers are confirmed and evaluator tests pass. Preserve all provenance and readiness checks; run one measured headed sample at a time on frozen final native source, installed binaries and exact saves.
